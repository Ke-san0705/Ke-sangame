# AI駆動開発形態 v2 ― GitHub Issue / Projects 駆動（2026-11-21）

原案：『AIのみで動かせるアプリ開発の開発形態（2026-11-20 案）』
本書は、2026-11-21に片山さんが回答した決定事項（新規リポジトリ／Codex Cloud前提／Gemini API＋チャットの併用／Figma正本／8時間ルール／定期チェック／Claude無料枠の指定チャット利用）を反映した改訂版。

## 1. 全体像

- 人間（片山さん）の仕事は「アイデア出し」「設計を変える提案への判断（8時間ルールあり）」「最終承認」の3つに絞る。
- 開発の場は **新規GitHubリポジトリ**。情報源はGitHub（Issue／PR／Projects／決定ログ）に一元化し、チャットは伝達と判断の場に限定する。
- 実行系はすべてクラウド側に置く。**PCを閉じていても開発が進む**ことが前提条件。
  - Codex：Codex Cloud（GitHub連携）で実装
  - Gemini API：クラウド実行（§6）
  - Muse（マル）：GitHub連携でIssue監視・操作、ブラウザでGeminiチャット／Claude無料枠チャットを操作

## 2. 役割分担

| 役割 | 担当 | 内容 |
|---|---|---|
| 統括PM・設計書作成・Issue監視／操作・最終レビュー・報告 | Muse（マル） | 仕様化、STEP分解、進捗管理、Gemini提案の取捨、片山さんへの報告 |
| 実装主軸 | Codex（Cloud） | コーディング、テスト作成、バグ修正。ブランチ／PR運用 |
| 評価・提案・補佐 | Gemini | 各STEP完了ごとの評価・変更案提案、UI面の助言、コーディング補佐 |
| 長期一発型の設計補助 | Claude無料枠（claude.ai） | 設計書の初稿生成など、枠を食う一発作業。マルが指定チャットをブラウザ操作して依頼する |
| 判断・承認 | 片山さん | アイデア、設計変更提案への判断（8時間無返答ならマルに委任）、最終承認 |

原則：**実装したAIが自分の成果物を最終判定しない**（実装＝Codex、判定＝Gemini＋Muse）。

## 3. STEPフロー（機能／プロジェクト1件あたり）

各STEPは「成果物」「担当」「完了条件」「Gemini評価」を持つ。STEPを積み上げて進み、飛ばさない。

### STEP 0：要求定義・プロンプト構築
- 担当：片山さん＋マル
- 成果物：要求メモ（何を作るか、なぜ必要か、成功の定義）
- 完了条件：後段のAIに渡すプロンプト（設計依頼文）が確定している

### STEP 1：設計書作成
- 担当：マル（必要に応じてClaude無料枠の指定チャットで初稿を生成し、マルが整える）
- 成果物：設計書（目的、画面／機能一覧、データ、処理フロー、未決定事項リスト）
- Gemini評価：実現可能性・抜け漏れの観点で評価コメントをIssueに残す

### STEP 2：UIモック作成
- 担当：Gemini＋マル（片山さんの案が起点）
- 成果物：**Figmaモックを正本**とする。新規の画像素材・デザイン案が必要な場合のみGemini画像生成を使う
- Geminiの関与：Geminiチャット（プロジェクト専用チャット）でUI案・配色・レイアウトの相談
- 完了条件：主要画面のモックがFigmaにあり、片山さんが方向性を確認済み（設計変更級なら§5の判断フロー）

### STEP 3：Issue分解・Project登録
- 担当：マル
- 成果物：GitHub Issue群（§4のテンプレート準拠）とProjectsボードへの登録
- 完了条件：各Issueに「担当AI」「完了条件（テスト名・画面・数値など機械判定できる形）」「試行上限」が書かれている
- **ここがゲート1**：Issue群の内容を片山さんが確認したら実装開始（ただし§5の8時間ルールを準用し、無返答でも停滞させない）

### STEP 4：Codex実装
- 担当：Codex Cloud
- 進め方：Issue単位でブランチ→PR。テスト同時作成を必須とする。PCが閉じていても進行する
- Gemini補佐：詰まった箇所の別解提案、UI実装の助言、コード片の補佐（API経由でマルが仲介）

### STEP 5：STEP毎レビュー（Gemini評価＋Museレビュー）
- 各PR／各STEP完了ごとに実施する
  1. CI自動テスト
  2. Gemini評価（§6の評価プロンプト雛形）：仕様適合、UI適合、リスク、変更案
  3. マルの最終レビュー：Gemini提案を取捨し、修正指示をIssue／PRに戻す
- 修正ループは最大3回。超えたら片山さんへエスカレーション

### STEP 6：最終承認・統合
- 担当：片山さん（ゲート2）
- 成果物：動作証跡（スクリーンショット／ログ）をPRに残す
- 承認後：マージと後処理はAI側で実行し、結果を報告する

## 4. GitHubの設計（リポジトリ／Projects／Issue）

### 4.1 リポジトリ
- 新規リポジトリを作成する（名前は最初のプロジェクト決定時に決める）。
- 必須ファイル：`README.md`（形態の概要）、`docs/design/`（設計書）、`docs/decisions/`（決定ログ）、`docs/usage-log.md`（§8のトークン台帳）。

### 4.2 GitHub Projects（ボード）― 採用を推奨
GitHubに詳しくなくても扱える最小構成にする。得られる幅は主に3つ。
1. **全体の見える化**：全Issueの状態（未着手／進行中／レビュー待ち／完了）が1画面で分かる
2. **STEP・担当AIでの絞り込み**：カスタムフィールドで「今どのSTEPで、誰がボールを持っているか」が追える
3. **自動化**：Issue／PRの状態変化でボードが自動で動く（手作業の更新が減る）

カスタムフィールド（最小限）：
- 状態（Status）：Backlog / Ready / In Progress / In Review / Done
- STEP：0〜6
- 担当AI：Muse / Codex / Gemini / 人間
- ゲート：なし / 判断待ち（時刻記録） / 最終承認待ち

### 4.3 Issueテンプレート（実装Issue）
```
## 目的（1〜2行）
## 対象STEP
## 入力（設計書・Figmaモックへのリンク）
## 完了条件（機械判定できる形で箇条書き）
## 試行上限（修正回数・前提条件）
## 担当AI / レビュー担当
## Gemini評価欄（STEP5で記入）
```

### 4.4 ラベル設計
- `step:0`〜`step:6`
- `ai:codex` `ai:gemini` `ai:Muse`
- `gate:decision`（片山さんの判断待ち。起票時刻を本文に記録し8時間ルールを適用）
- `type:design` `type:ui` `type:impl` `type:review`
- `blocked`（エスカレーション中）

## 5. 判断フローと8時間ルール（停滞回避）

- Gemini提案やレビュー指摘のうち、**設計を変えないもの**はマルが取捨して進める。
- **設計を変える提案**は、マルがこのサイドチャット（GitHub issueでAI駆動開発設計）に「提案内容・推奨・影響範囲」を投稿して片山さんの判断を待つ。
- **投稿から8時間返答がなければ、マルが判断して進める**。判断内容と理由は該当Issueの決定ログ（`docs/decisions/`）に必ず残し、次回の報告で事後報告する。
- 例外（8時間を待たず即時停止して報告）：費用が発生する／外部公開が絡む／個人情報を扱う変更／取り消せない操作。この4つは無返答でも実行しない。

## 6. Geminiの使い方（API＋チャット併用）

### 6.1 Gemini API（自動実行系）
- 用途：STEP毎評価（STEP1・STEP5）、変更案の定型生成、コーディング補佐の定型タスク
- キー：片山さんがGoogle AI Studioで取得し、Secure Vault経由で保管。チャット本文にキーを貼らない
- 実行場所：Codex Cloudと同じく**クラウド側**とし、**主経路はGitHub Actions**（2026-11-21確定）。マルのクラウド環境からの呼び出しは補助・緊急用とする。PCには依存しない。キーはGitHub側ではSecretsに登録する
- モデル：指定なし。当面は評価タスクに適したモデルをマルが選定し、台帳（§8）に使用モデルと使用量を記録する
- 評価プロンプト雛形（STEP5用）：
```
あなたは実装者ではない第三者レビュアーです。以下の設計書・Figma説明・PR差分について、
1) 仕様適合（満たしていない完了条件を列挙）
2) UI適合（モックとの差異）
3) リスク（不具合・保守性）
4) 変更案（ある場合のみ。設計を変える案は「設計変更級」と明記）
を出力してください。推測で仕様を広げないこと。
```

### 6.2 Geminiチャット（対話系）
- 用途：UI案、発想寄りの相談、API化しにくい探索的な相談
- 運用：プロジェクトごとに専用チャットを立て、マルがブラウザで操作する。やり取りの結論は必ずGitHub Issue／決定ログへ転記し、チャット内にだけ残さない

## 7. Claude無料枠の使い方
- 対象：claude.aiのWebチャット。**片山さんが指定したチャット**をマルがブラウザ操作して使う（URLはサイドチャットの2026-11-21メッセージにあり、本書には転記しない）。
- 用途を「設計書の初稿のような長期一発型」に限定し、無料枠を細切れに使わない。
- 成果物はマルが受け取り、整形・検証してから設計書としてリポジトリに入れる（Claudeの出力を無検証で正本にしない）。
- 前提：マルのブラウザでclaude.aiにサインインできていること。できない場合は片山さんのライブブラウザ引き継ぎが必要。

## 8. トークン使用量・制限の可視化（希望事項：実現できる範囲で）

台帳ファイル `docs/usage-log.md` をリポジトリに置き、STEP毎に記録する。可視化できる範囲はAIごとに異なるため、取得方法を正直に分ける。

| 対象 | 取得できるもの | 方法 | 限界 |
|---|---|---|---|
| Gemini API | 入力／出力トークン数（レスポンスのusage情報）、使用モデル、回数 | API呼び出し時に自動で台帳へ追記 | 最も正確に取れる |
| Codex Cloud | タスク単位の実行有無・PR結果。使用量の数値はChatGPT／Codex側の利用状況表示に依存 | マルが確認できた範囲で台帳に転記 | API的な自動取得は不可。数値が取れない場合は「取得不可」と明記 |
| Claude無料枠（Web） | 使用回数と日時、依頼内容 | マルが操作時に台帳へ記録 | トークン数の表示がないため数値化は不可。枠の残量は不透明 |
| GitHub Actions（使う場合） | 実行時間（分） | Actionsの実行履歴から転記 | トークンではなく時間の指標 |

- 台帳の目的は「どのSTEPでどれだけ消費したか」の把握と、無料枠に近づいた段階での早期警告。
- 残量アラートの目安：Gemini APIは無料枠の上限に近づく使い方になった時点で報告。Claude無料枠は制限メッセージが出たら即報告し、そのSTEPはマル側で代替する。

## 9. 定期チェック（監視）
- 開発がアクティブな期間は、マルがGitHub（Issue／PR／Projects）を定期チェックし、進展・詰まり・判断待ち（§5）をこのサイドチャットへ報告する。
- チェック間隔（2026-11-21確定）：開発がアクティブな期間は**3時間おき**にチェックし、朝ブリーフィングにも統合して報告する。
- チェックは読み取り中心。Issueへの書き込み・操作は本書の権限範囲（§3・§5）内でのみ行う。

## 10. 最小実証（パイロット）の選び方 ※設計ごとに決める
**最初のプロジェクト（2026-11-21決定）：計算力を鍛えるアプリ。** Webサイト形式でも可。誰でも簡単に使え、寿司打のように気軽に遊んで計算力が鍛えられるものを目指す。詳細仕様はSTEP 0で片山さんへの質問を通じて固める（質問票は別紙 `pilot-calc-app-step0-2026-11-21.md`）。
候補は固定しない。各設計（プロジェクト）の開始時に、次の観点で1件選んで本書の付属メモに記録する。
- 小さい：1〜2日相当のAI作業で一巡できる規模
- 証跡が残る：PR・テスト・スクショで成否が第三者に分かる
- 壊れても痛くない：本番データ・外部公開に直結しない
- STEP2（UI）とSTEP5（Gemini評価）の両方が実際に発生する題材であること
